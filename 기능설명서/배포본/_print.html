01. 시스템 구조

1. 등장인물 셋 — 권한이 다르다

이름역할할 수 있는 것할 수 없는 것
위임자이순자 (어머니)delegator위임 설정, 위임장 서명, 결제 승인/거부, 위임 정지·복구—
대리인이지은 (딸)delegate결제 요청, 한도 상향 요청승인 불가
공동보호자이준호 (아들)guardian예외 건 알림 수신, 이의제기, 확인결제 권한 자체가 없음
보호자에게 결제 권한을 주지 않은 것이 설계의 핵심입니다. 주는 순간 "판단 능력이 약해진 분에게 매번 확인을 받는다"는 의사능력 모순이 되살아납니다. 보호자는 결제의 당사자가 아니라 감시자입니다.

권한은 화면에서만 가리는 것이 아니라 서버가 거부합니다 (api/state.js의 ALLOW 표). 클라이언트를 고쳐도 403이 돌아옵니다.

4. 결제 한 건이 흐르는 길

① 대리인이 결제 요청
     ↓
② judge() 판정
     ↓
③ 자동승인 조건을 보는가?
     ├─ 신뢰 기관 + 정상 + 한도 내   → 즉시 승인. 아무것도 묻지 않음 (보호자 알림함에 기록만)
     ├─ 공과금 월 정기 + 정상        → 즉시 승인
     ├─ 처음 가는 병원 (정상이어도)   → 보호자 알림 + 위임자 확인
     ├─ 평소와 다름 (confirm)       → 보호자 알림 + 위임자 확인
     └─ 보류 (hold)                → 결제 안 됨 + 보호자 알림
     ↓
④ 보호자(아들) 이의제기 → 보류 중이면 묶고, **이미 나간 건이면 장부를 되돌림**
     ↓
⑤ 위임자(어머니) 승인 화면 → PIN 인증 → 승인/거부
     ↓
⑥ 온체인 기록 (이벤트 원문의 SHA-256 해시만)

일상 결제는 건별로 묻지 않습니다. 위임자가 치매·인지질환이면 건별 승인 자체를 수행하지 못하므로, 매번 묻는 설계는 서비스 전제와 모순입니다. 설정 시점의 위임장 서명으로 동의를 갈음하고, 평소와 다른 건만 알리거나 보류합니다. 다 물으면 알림 스팸이 되고, 다 자동이면 통제가 없습니다.

4-1. 신뢰 기관 — 무엇을 면제하고 무엇을 면제하지 않는가

"자주 가는 병원은 묻지 않는다"의 정확한 범위입니다.

축보는 것신뢰 기관이면
결제처심평원 등록? 서명 유효?면제 — 그것이 신뢰의 의미
금액평소 대비 편차 (z)그대로 검사
빈도·패턴한도 아래로 쪼개는가그대로 검사
한도건당·월·생활비 보호선그대로 검사
"재검토 없이"가 아니라 "확인 요청 없이"입니다. 검사는 조용히 다 돌고, 통과하면 묻지 않습니다. 결제처 축까지 끄면 신뢰 기관에서 한도 아래로 쪼개는 공격이 그대로 통과해, 구조화 탐지가 스스로 만든 구멍으로 사라집니다. 실제로 고령자 금융착취는 가짜 병원보다 진짜 병원에서 과다하게 쓰는 쪽이 흔합니다.

신뢰 기관은 두 경로로 채워집니다.

경로내용
(c) 자동위임 전에 위임자가 본인 명의로 결제한 원장에서 3회 이상 방문한 곳을 자동 등록
(a) 수동위임 설정 화면 "자주 가는 병원 · 확인 없이 결제" 카드에서 직접 추가·해제

(c)가 콜드스타트를 그대로 해결합니다. 실서비스에서 이 데이터는 은행이 이미 보유한 카드·계좌 거래내역에서 나오므로 새로 모을 것이 없습니다.

데모는 그 상태를 42건짜리 원장(PAST_LEDGER)으로 재현합니다. 판정의 μ·σ도, 신뢰 기관도 전부 이 원장 하나에서 도출됩니다 — 하드코딩한 목록이 아닙니다.

1~2회만 간 곳은 아직 신뢰가 아닙니다. 가끔 간 곳까지 자동으로 열어주면 신뢰의 근거가 약해집니다. 기관별 평균이 종별 본인부담률 서열과 같은 방향으로 나오는 이유는 02. 판정 엔진의 "기준 분포" 절에 있습니다.

(a)는 공공데이터 목록에 있는 기관만 고를 수 있습니다. 손으로 이름을 적게 하면 위임자를 설득해 가짜 병원을 신뢰 목록에 올릴 수 있습니다.

등록된 곳은 대리인 결제 화면에도 버튼으로 뜹니다. 딸이 매번 병원 이름을 검색하지 않고 탭 한 번으로 고릅니다.

⚠ 그 버튼 묶음의 라벨은 "어머니가 등록한 자주 가는 곳" 이지 "확인 없이 결제됩니다" 가 아닙니다. 결제 요청 화면은 대리인(감시 대상)이 보는 곳이라, 어디가 마찰이 가장 낮은지 알려주는 것은 반사실 임계값을 노출하는 것과 같은 성격의 문제입니다. 편의만 주고 우회 힌트는 주지 않습니다.

4-2. 사후 되돌리기 — 이미 나간 건

자동승인을 늘리면 "막지 못하고 알림만 가는" 건이 생깁니다. 그 대가를 받는 장치입니다.

왜 사용자 화면에서 숫자를 뺐나 (2026-10-13)

반사실이 "₩185,578 이하였으면 통과됐습니다" 라고 임계값을 찍고 있었습니다. 결제 요청 화면은 대리인이 보는 곳이라, 이 숫자는 곧 탐지를 피하는 최적 금액이 됩니다.

결제는 즉답이어야 하고, 공공 API는 점검·장애가 잦습니다. 판정 경로에 외부 의존성을 넣으면 API가 멈출 때 사칭 탐지가 통째로 멈춥니다. 그래서 결제는 스냅샷으로만 판정합니다.

청구서 QR에 기관·금액·날짜·청구서번호가 담긴 서명 payload가 이미 들어 있습니다. 결제 요청과 필드 대조만 하면 매칭이 성립합니다. 종이 영수증 OCR은 실서비스 확장 범위이고 이 프로토타입의 구현 범위가 아닙니다.

해시는 한 방향입니다. 나중에 다툼이 생기면 금고에서 원문을 꺼내 해시를 다시 떠서 체인의 것과 맞춰보면 됩니다 — 내용은 보여주지 않고 진짜라는 것만 증명합니다.

조회 키에 salt를 섞는다 (2026-10-07 적용)

전  →  key = SHA-256("DLG-2026-0914")                      ← 후보 수천 개, 전수 대입으로 복원
후  →  key = SHA-256("DLG-2026-0914|7b41e9d2a8c05f36")      ← salt를 모르면 특정 불가

위임 ID가 DLG-연도-월일 형식이라 후보가 수천 개뿐이었습니다. 해시가 약한 게 아니라 재료의 후보가 적은 것이 문제였습니다(현관 비밀번호를 생일로 둔 것과 같습니다). 규칙은 contracts/scripts/hash.js의 delegationKey()에 있고, 프런트엔드와 동일합니다.

05. 백엔드와 실사용 모드

멘토 지적 "백엔드 + 로그인 + 배포 — 실제로 열어보게" 에 대한 대응입니다. Vercel 서버리스 함수 4개로 구성되어 있습니다 (carepass-prototype/api/).

1. 왜 서버가 필요한가

데모 계정 3개가 하나의 가구(household)를 공유합니다. 어머니가 권한을 주고, 딸이 결제를 요청하고, 아들이 예외만 통지받습니다. 세 사람이 각자 기기에서 로그인해도 같은 데이터를 봅니다 — 그것이 이 서버의 존재 이유입니다.

3. 인증 — 서버가 검증한다

  • 아이디+비밀번호를 서버가 확인합니다.
  • 비밀번호는 길이가 달라도 타이밍이 새지 않도록 SHA-256 해시를 떠서 상수시간 비교합니다

(crypto.timingSafeEqual).

  • 존재하지 않는 아이디도 더미 값과 비교해 아이디/비밀번호를 구분해 거부하지 않습니다.
  • 세션은 HMAC-SHA256 서명된 HttpOnly 쿠키입니다. 만료 7일.

서명 비교도 상수시간이고, 길이가 다르면 즉시 거부합니다.

토큰 = base64url({a: 계정, iat, exp}) + "." + HMAC-SHA256(본문, SESSION_SECRET)

환경변수: SESSION_SECRET, CP_PW_DELEGATOR / CP_PW_DELEGATE / CP_PW_GUARDIAN, 그리고 HIRA_API_KEY (심평원 Open API 인증키 — 서버에만 두고 브라우저로 내려보내지 않습니다)

4. 역할 권한 — 클라이언트를 고쳐도 서버가 막는다

06. 확장 기능

1. 공동보호자 — 결제 권한 없는 감시자

아들 이준호(공동보호자)는 결제 권한이 없습니다. 평소와 다른 건만 통지받고 이의제기합니다.

기능동작
보호자 알림함예외 건은 배지를 울리고, 자동승인 건은 조용히 기록만
이의제기 (보류 중)사유를 고르면 해당 결제가 실제로 보류되고 위임자 승인 화면에 배지가 뜸
이의제기 (이미 나간 건)장부 롤백 + 신뢰 해제 + 온체인 증거 고정 — 아래 참조
확인(ack)문제없음으로 닫기
온체인guardianNotified / guardianObjection / guardianAcknowledged / paymentDisputed

이의제기 사유는 셋 중에서 고릅니다 — 어머니가 요청한 적 없는 결제 / 금액이 과도함 / 병원 방문 사실이 없음. 기록으로 끝내지 않고 해당 건을 실제로 묶는 것이 핵심입니다.

사후 되돌리기 — 이미 집행된 건

자동승인을 늘리면 "막지 못하고 알림만 가는" 건이 생깁니다. 그 대가를 받는 장치입니다.

집행된 건에 이의제기
  → 상태 disputed
  → 위임 풀 잔액 · 월 사용액 롤백
  → 신뢰 기관에서 해제 (그 병원은 다시 확인을 거침)
  → 대리인 의심 전환 (이후 보호자 알림 비통지)
  → paymentDisputed 온체인 기록

한도 롤백이 중요한 이유는 성능평가에서 나왔습니다. '월 한도 초과' 보류 160건 중 120건이 사기가 한도를 먼저 소진해 뒤따르는 정상 결제가 막힌 연쇄입니다. 사기의 2차 피해가 "어머니가 정작 필요한 병원비를 못 쓰는 것" 으로 나타나고, 롤백이 그 연쇄를 끊습니다.

구조화 탐지가 봐야 할 공격 패턴 증거(S.recent)는 지우지 않습니다.

⚠ 앱은 돈을 되찾지 못합니다. 카드 거래취소·착오송금 반환은 은행 분쟁처리와 가맹점 동의 또는 법적 절차가 필요합니다. 앱은 확산을 끊고, 장부를 정리하고, 증거를 고정하는 데까지만 합니다. 그래서 빨리 잡는 것이 중요합니다 — 가맹점 정산 전이면 취소가 쉽고, 후면 어렵습니다. 성능평가의 "차단 시점 2.4 → 2.0번째, 유출액 29% 감소" 가 정확히 이 가치입니다.

블록체인을 쓰는 이유가 여기서 완성됩니다. 그동안 온체인 기록은 "기록한다"에서 끝났습니다. 사후 이의제기는 그 기록이 실제로 쓰이는 장면입니다 — 가족 간 분쟁에서 "내가 승인했다/안 했다"가 다툼이 될 때, 은행 DB는 운영자가 고칠 수 있어 증거력이 약하지만 결제 시점에 체인에 박힌 해시는 누구도 바꿀 수 없습니다.

FINRA 4512 식 비통지 분기

보호자 자신이 의심 대상일 때는 통지하지 않는 경로가 있습니다. 은닉 SOS가 발동하면 S.suspectDelegate = true가 되고, 이후 모든 보호자 알림은 silent 플래그가 붙어 대리인에게 통지되지 않습니다. 온체인 사유에도 · 대리인 비통지(FINRA 4512)가 함께 기록됩니다.
