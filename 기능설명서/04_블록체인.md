## 2. 컨트랙트 — `CarePassRegistry`

두 가지를 담는 **공개 장부**입니다.

### ① 위임·결제 이력

```solidity
struct Record {
    bytes32 dataHash;  // 오프체인 이벤트 원문(JSON)의 SHA-256
    uint256 ts;        // 기록된 블록 시각
    string  fn;        // 이벤트 종류
}
registerDelegation(bytes32 id, bytes32 dataHash, string fn)   // 기록 계정만
getHistory(bytes32 id) → Record[]                              // 누구나 조회
```

### ② 의료기관 인증 — 여러 은행·결제대행사·지자체가 함께 조회하는 공용 명부

```solidity
struct Institution {
    bytes32 keyX, keyY;   // 기관 서명키(ECDSA P-256) 공개키 좌표
    bytes32 proofHash;    // 인증 근거(심평원 목록 해당 행)의 SHA-256
    uint64  issuedAt;     // 0 = 발급된 적 없음
    uint64  revokedAt;    // 0 = 유효
    string  name;         // 기관명 (공개 정보)
}
certifyInstitution(...)  / revokeInstitution(...)   // 기록 계정만
institutionKey(bytes32)  / isCertified(bytes32)     // 누구나 조회
```

### 권한 모델

| | `registerDelegation` · `certifyInstitution` · `revokeInstitution` | `getHistory` · `institutionKey` |
|---|---|---|
| 누가 | **기록 계정(recorder)만** — 실서비스에서는 은행 기록 서버 키 | **누구나** |
| 왜 | 제3자가 가짜 이력이나 가짜 인증 기관을 끼워 넣지 못하게 | 제3자 검증 가능성 확보 |

## 4. 프라이버시 — 오픈 체인인데 결제내역이 안 보이는 이유

### 원문은 처음부터 올리지 않는다

| 온체인에 **올라가지 않음** | 온체인에 올라감 |
|---|---|
| 금액 · 결제처 · 카테고리 | 이벤트 원문의 SHA-256 `dataHash` |
| 이름 · 계좌번호 | 위임 조회 키 |
| 위임장 원문 · 서명 이미지 | 위임장 해시 · 서명 해시 |
| 청구서 원문 | 기관 공개키 · 기관명 *(공개 정보라 의도적)* |

해시는 **한 방향**입니다. 나중에 다툼이 생기면 금고에서 원문을 꺼내 해시를 다시 떠서
체인의 것과 맞춰보면 됩니다 — **내용은 보여주지 않고 진짜라는 것만 증명**합니다.

### 조회 키에 salt를 섞는다 (2026-10-07 적용)

```
전  →  key = SHA-256("DLG-2026-0914")                      ← 후보 수천 개, 전수 대입으로 복원
후  →  key = SHA-256("DLG-2026-0914|7b41e9d2a8c05f36")      ← salt를 모르면 특정 불가
                                     └ 위임별 난수. 오프체인(은행)에만 보관
```

위임 ID가 `DLG-연도-월일` 형식이라 **후보가 수천 개뿐**이었습니다. 해시가 약한 게 아니라
**재료의 후보가 적은 것**이 문제였습니다(현관 비밀번호를 생일로 둔 것과 같습니다).
규칙은 `contracts/scripts/hash.js`의 `delegationKey()`에 있고, 프런트엔드와 동일합니다.

### 아직 가려지지 않는 것 — 정직하게

체인은 **여전히 공개**입니다. 읽는 것을 막은 것이 아닙니다.

| 복원 불가 | 아직 노출 |
|---|---|
| 금액 · 기관 · 사람 · 위임 내용 | 이벤트 **건수** |
| | 블록 **타임스탬프** |
| | 이벤트 **종류** — `string fn`이 평문 |

**일기 내용은 안 보이지만, 일기를 몇 번 언제 썼는지는 보이는 상태**입니다.
특히 `sosAlert`가 평문으로 남는 것은 은닉 SOS의 전제와 모순입니다 — 다음 단계에서 코드화합니다.
(현재 Sepolia에 실제 기록된 3건은 `delegationConfigured`·`paymentApproved`뿐이고
런타임 이벤트는 로컬 시뮬레이션이라 라이브 결함은 아닙니다.)

## 5. 온체인 검증 흐름 — 화면이 실제로 체인을 읽는다

```
페이지 로드
  → 공개 노드(publicnode)에 eth_call: getHistory(delegationKey)
  → ABI 디코딩 (bytes32 dataHash, uint256 ts, string fn)[]
  → 원문(contracts/demo-events.json)으로 다시 계산한 SHA-256과 대조
  → 인스펙터 '블록체인 원장' 탭에 verified / mismatch / offline 표시
```

RPC 타임아웃은 7초이고, 목록의 노드를 순서대로 시도합니다.
**전부 실패하면 `offline`로 떨어지고 로컬 기록으로 자동 전환**되므로 시연이 멈추지 않습니다.

> 2026-10-13 전수 검증 시점 기준 실제 조회 결과: **`verified` · 온체인 3건**
