# 03. 기관 인증과 청구서 검증

병원 사칭을 **두 겹**으로 막습니다. 첫 겹은 공공데이터, 둘째 겹은 전자서명입니다.

## 1. 첫 겹 — 공공데이터 결제처 확인

데이터를 **두 가지 방식으로** 씁니다. 역할이 다릅니다.

| | 내장 스냅샷 (파일) | **Open API (실시간)** |
|---|---|---|
| 출처 | 「전국 병의원 및 약국 현황」 2026.6. | 병원정보서비스 · 약국정보서비스 |
| 범위 | 대구 5,607곳 | 전국 · 실시간 |
| 쓰는 곳 | **결제 판정** | **기관 등록** (신뢰 기관 추가 · 인증 발급) |
| 라이선스 | 공공누리 제1유형 | 공공누리 제1유형 · 무료 · 일 10,000회 |

병원비 항목의 결제처가 목록에 없으면 **금액이 작아도 자동 보류**합니다.

```
결제처 "○○메디컬센터" 90,000원
  → 심평원 요양기관 목록(대구)에 없음
  → hold · "병원을 사칭한 결제일 수 있어 결제를 임시 보류합니다"
```

### 왜 결제 판정에는 API를 쓰지 않는가

**결제는 즉답이어야 하고, 공공 API는 점검·장애가 잦습니다.** 판정 경로에 외부 의존성을 넣으면
API가 멈출 때 **사칭 탐지가 통째로 멈춥니다.** 그래서 결제는 스냅샷으로만 판정합니다.

| | 결제 판정 | 기관 등록 |
|---|---|---|
| 빈도 | 매 결제 | 가입 시 몇 번, 이후 가끔 |
| 지연 허용 | ❌ 즉답 | ✅ "확인 중…" 1~2초 |
| 실패하면 | **탐지가 통째로 멈춤** | 등록만 안 됨. 결제는 영향 없음 |

### 등록 시점 조회가 메우는 구멍

스냅샷은 2026.6. 기준이라 **그 뒤 폐업한 기관이 목록에 남아 통과합니다.** 온체인 기관 인증은
폐업을 반영(`revoke`)하는데 결제처 목록은 못 하는 모순이 있었습니다. 등록 시점 조회가 이를 닫습니다.

```
신뢰 기관 추가 / 인증 발급
  → GET /api/hira?region=대구&name=대구의료원
  → 심평원 실시간 조회
     ├─ 있음 → 등록. 온체인 사유에 "심평원 Open API 실시간 확인" 기록
     ├─ 없음 → 등록 거부. "폐업·휴업일 수 있어 등록하지 않았습니다"
     └─ 실패 → 내장 스냅샷으로 그대로 진행 (폴백)
```

**실패해도 아무 일도 일어나지 않습니다.** 키 미설정·타임아웃·점검·한도 초과 중 무엇이든
내장 목록으로 떨어집니다. 심사장에서 네트워크가 막혀도 동작이 같습니다
(검증: API 없는 환경에서 등록 **10ms** 완료).

### 프록시를 거치는 이유 — `api/hira.js`

| 이유 | 내용 |
|---|---|
| **인증키 보호** | 단일 HTML에 `serviceKey`를 박으면 공개 저장소와 배포본에 그대로 노출됩니다. 계정에 묶인 키라 도용되면 한도가 소진됩니다 |
| **CORS** | data.go.kr는 브라우저 직접 호출이 막히는 게 일반적입니다 |
| **한도 보호** | 24시간 캐시 + 분당 60회 상한 (일일 10,000회 대비) |
| **키 형식** | Encoding/Decoding 키를 `%` 유무로 자동 판별 — 재인코딩하면 인증이 깨집니다 |
| **약국 분기** | 병원 목록에 없으면 약국 API를 자동으로 조회합니다 (별도 서비스) |
| **지역 필터** | `yadmNm`은 **부분일치**라 "대구약국"에 포항·의성 약국까지 딸려 옵니다. 주소로 좁힙니다 (전국 10건 → 대구 4건) |

`/api/health`가 `"hira": true/false`로 **키 설정 여부만** 알립니다. 값은 내보내지 않습니다.

> **다음 단계** — 등록 **후에** 폐업한 기관은 신뢰 목록에 남습니다. 신뢰 기관은 묻지 않고 승인하므로
> 오히려 더 위험합니다. **신뢰 목록만 하루 1회 재점검**해 폐업이 확인되면 자동으로 신뢰를 해제하고
> 온체인 인증도 `revoke`하는 배치가 필요합니다. 결제 경로가 아니므로 지연·가용성 문제가 없고,
> 서버가 기관 마스터를 갱신하는 형태면 **호출량이 가구 수와 무관**해집니다.

**첫 겹의 한계는 그대로입니다.** 목록에 있는 **이름을 그대로 베끼면** 통과합니다. 그래서 둘째 겹이 필요합니다.

## 2. 둘째 겹 — 기관 전자서명

### 구조

```
① 심평원 목록으로 실재가 확인된 기관에 인증 발급
     ↓  기관 식별자  instId = SHA-256("기관명|종별|구군")   (기관명은 공백 제거)
     ↓  인증 근거    proofHash = SHA-256(요양기관 목록 해당 행)
② 기관의 서명 공개키(ECDSA P-256의 X·Y 좌표)를 온체인에 등록
③ 병원이 청구서에 전자서명 → QR로 전달
④ 앱이 온체인에서 공개키를 조회해 WebCrypto로 서명 검증
```

### 서명 대상 원문

키 순서가 서명·검증 양쪽에서 같아야 하므로 고정합니다 (`sig` 자신은 제외).

```js
JSON.stringify({ v, invNo, instId, inst, type, gu, cat, amount, items, issuedAt, nonce })
```

### 공개키 출처 3단 폴백

| 표시 | 의미 |
|---|---|
| `onchain` | **온체인 인증 목록에서 병원 공개키를 조회**했습니다 |
| `builtin` | 노드에 연결하지 못해 **앱에 내장된** 인증 목록으로 확인했습니다 |
| `local` | **이 단말에서 발급한** 인증으로 확인했습니다 (인스펙터에서 직접 발급한 경우) |

온체인 조회는 `institutionKey(bytes32)` (셀렉터 `0x81322425`)를 `eth_call`로 읽습니다.

### 검증 결과 4종

| `chk` | 의미 | 판정 |
|---|---|---|
| `ok` | 등록 공개키와 서명이 일치 | 통과 |
| `sigFail` | **이름은 같은데 서명이 맞지 않음** — 사칭 | **hold** |
| `revoked` | 인증이 취소된 기관 (폐업·자격정지·키 유출) | **hold** |
| `uncertified` | 서명을 검증할 공개키가 인증 목록에 없음 | confirm |

> 데모에는 **진짜 청구서**와 **이름까지 베낀 사칭 청구서**가 들어 있습니다.
> 둘 다 "대구의료원"이라고 적혀 있지만, 사칭본은 서명 검증에서 걸립니다.

### 인증 취소도 체인에 남는다

`revokeInstitution(instId, reason)` — 폐업·자격정지·서명키 유출 시 호출합니다.
취소 이력 자체가 온체인에 남고, 취소된 기관은 **새 서명키로 다시 인증받을 수 있습니다**(자격 회복·키 교체).

실제 기록: [○○재활요양병원(시연용) 인증 취소](https://sepolia.etherscan.io/tx/0xed4ad6fe52d5274b924e657318dcb7a180091f57f9d26a1ad47ce6d468096e25)

## 3. 청구-결제 매칭 — 5항목 대조

서명이 통과해도 **청구서와 실제 결제가 다를 수 있습니다.** 그 구멍을 탐지로 바꿨습니다.

| # | 항목 | 검사 | 불일치 시 |
|---|---|---|---|
| 1 | 기관 전자서명 | 등록 공개키와 일치하는가 | **hold** |
| 2 | 발행 기관 ↔ 결제처 | 청구서 발행 병원 = 결제처인가 | **hold** |
| 3 | 청구 금액 ↔ 결제 금액 | 금액이 같은가 | **hold** |
| 4 | 발행일 | 0일 ≤ 경과 ≤ **14일** (미래 날짜도 거부) | confirm |
| 5 | 중복 사용 | 이미 결제에 쓰인 청구서 번호인가 | **hold** |

승인되면 해당 청구서 번호를 **소모 처리**(`S.usedInv`)해서 재사용을 막습니다.

### 왜 OCR이 필요 없는가

청구서 QR에 **기관·금액·날짜·청구서번호가 담긴 서명 payload**가 이미 들어 있습니다.
결제 요청과 **필드 대조만 하면** 매칭이 성립합니다. 종이 영수증 OCR은 실서비스 확장 범위이고
이 프로토타입의 구현 범위가 아닙니다.

### 막아내는 수법

```
수법: 병원 A가 서명한 진짜 청구서를 들고, 결제처만 병원 B로 바꿔 결제
      → 서명은 유효하므로 1번 검사는 통과
      → 2번(발행 기관 ↔ 결제처)에서 걸림 → hold
```

이 시나리오의 **z-score는 0.52** 입니다. 금액만 보는 축으로는 전혀 잡히지 않습니다.
