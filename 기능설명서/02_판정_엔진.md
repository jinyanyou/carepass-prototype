# 02. 판정 엔진 — `judge()`

결제 한 건을 받아 `approve / confirm / hold` 중 하나와 **사람이 읽을 수 있는 사유**를 돌려줍니다.
구현 위치: `carepass-prototype/index.html` 의 `judge(catKey, amount, merchant)`.

## 1. 규칙이 쌓이는 순서

위에서 아래로 검사하며, **뒤 규칙이 앞 판정을 뒤집지 못합니다**(`level==='normal'`일 때만 올림).

| 순 | 검사 | 결과 |
|---|---|---|
| 1 | 청구서 전자서명 불일치 (`sigFail`) | **hold** |
| 2 | 인증 취소된 기관의 청구서 (`revoked`) | **hold** |
| 3 | 청구서 금액 ≠ 요청 금액 | **hold** |
| 4 | 미인증 기관 청구서 (`uncertified`) | confirm |
| 5 | 청구-결제 **기관 불일치** | **hold** |
| 6 | 청구서 **중복 사용** | **hold** |
| 7 | 청구서 유효기간(14일) 경과 | confirm |
| 8 | **미등록 의료기관** (심평원 목록에 없음) | **hold** |
| 9 | **구조화(분할 결제) 적중** | **hold** |
| 9' | 구조화 경고 (한 번 모자람) | confirm |
| 10 | 사용처 화이트리스트 위반 | **hold** |
| 11 | 위임 풀 잔액 초과 | **hold** |
| 12 | 생활비 보호선 미달 | **hold** |
| 13 | 건당 한도 초과 | **hold** |
| 14 | 월 누적 한도 초과 | **hold** |
| 15 | **z ≥ 3** | **hold** *(앞 규칙이 전부 통과했을 때만)* |
| 15' | **z ≥ 2** | confirm *(〃)* |
| 16 | 고액 구간(≥50만) | confirm |

규칙에 하나도 걸리지 않으면 사유에 `규칙 위반 없음 · z=... (정상 범위)`가 적힙니다.

### z-score의 위상 — 중요

**z만으로 판단하지 않습니다.** z 분기에는 `if(level==='normal')` 조건이 붙어 있어,
앞의 규칙이 하나라도 걸리면 **z는 사유 목록에 증거로만 기록되고 판정을 바꾸지 못합니다.**

다만 **다른 규칙이 전부 통과하고 z ≥ 3이면 z 단독으로 보류**가 됩니다.

| 상황 | z의 역할 |
|---|---|
| 사칭·서명실패·매칭불일치·구조화·한도초과·보호선 미달 중 하나라도 해당 | 증거로 기록만 |
| 나머지 규칙 통과 + z ≥ 3 | **단독으로 보류** |
| 나머지 규칙 통과 + z ≥ 2 | 보호자 확인 |
| z < 2 | 영향 없음 |

> ⚠ `eval/REPORT.md` 5-6의 **결정 4 2단 설계**(마찰 9.8% → 0.8%)는 *z 단독 보류를 알림으로 내린*
> 상태에서 계산한 수치입니다. 현재 앱은 보수적으로 **전부 보류**합니다. 발표에서 이 차이를
> 먼저 밝히는 편이 안전합니다.

### z 임계 3의 근거

관례가 아니라 **오탐율 기준으로 역산**한 값입니다. 평가셋에서 z=3.0은 **오탐율 1.37%** 지점이고,
1% 이하로 조이려면 z ≥ 3.3이 필요한데 그때 정탐율이 2%p 더 떨어집니다.

### 기준 분포

평소 결제 분포는 **로그정규(중앙값 85,000 · σ_log 0.45)** 로 생성합니다.
초기에는 정규분포를 2만~19만으로 잘라 썼는데, **절단은 σ를 과소추정시켜 z를 부풀립니다**(= 오탐 증가).
평가셋과 같은 분포로 교체한 뒤 σ가 32,155 → 44,396(+38%)로 올라갔습니다.

## 2. 구조화(한도 회피) 탐지 — 킬러 차별점

> *"사기범이 한도 바로 아래로 쪼개서 결제하면?"* 에 대한 답입니다.
> 금액 하나만 보는 z-score로는 **절대 안 잡힙니다.**

```js
const STRUCT_WINDOW_DAYS = 7;   // 관찰 창
const STRUCT_NEAR        = 0.9; // 건당 한도의 90% 이상이면 "한도 근접"
const STRUCT_MIN         = 3;   // 창 안에 3회 이상이면 적중
```

| 판정 | 조건 |
|---|---|
| `hit` (보류) | 이번 결제가 한도 근접 **그리고** 7일 내 근접 결제가 **3회 이상** |
| `warn` (확인) | 같은 조건에서 2회째 |

**시연값**: 건당 한도 150,000 / 결제 145,000(97%) / 3일간 반복 → 7일 내 4회, 누적 580,000.
이때 **z = 1.086** 으로 임계(3) 한참 아래입니다 — *"z로는 정상인데 다른 축이 잡는다"* 가
코드에서 사실입니다.

> ⚠ **이 금액은 바꾸면 안 됩니다.** 처음에는 29만원(한도 30만)으로 짰는데 z=6.0이라
> z-score도 같이 잡아버려서 주장이 성립하지 않았습니다.

## 3. 반사실 설명 (XAI) — "무엇이 달랐으면 통과였나"

고령자에게 가장 이해하기 쉬운 설명 형태입니다. 다만 **우회 힌트를 주지 않는 것**이 핵심입니다.

| 차단 종류 | 설명 |
|---|---|
| 금액으로 풀리는 것 | *"₩300,000 이하였으면 통과됐습니다. (가장 먼저 걸린 기준: 건당 한도)"* |
| 사칭 · 서명 실패 · 매칭 불일치 · 구조화 · 항목 차단 | *"**금액을 낮춰도 통과되지 않습니다** — 결제처 등록 문제입니다."* |

금액 기준은 네 개 중 **가장 먼저 걸리는 것**을 고릅니다 — 건당 한도 / 월 한도 잔여 /
생활비 보호선 여유 / 평소 패턴(μ+2σ).

**빈도 쪽 반사실**도 따로 있습니다 — *"평소 이 결제처는 월 2회 수준인데 이번 주 4회째입니다."*

## 4. 탐지 성능평가

`carepass-prototype/eval/` — 재현: `python gen_dataset.py && python evaluate.py && python make_chart.py`

**평가셋**: 120가구 × 180일 = 2,833건, 채점 1,985건(이상 162건·8.2%), 앞 60일은 baseline 추정용 번인.

**자기충족 회피**: 이상치를 '규칙 위반'이 아니라 **사기범의 목표·행동**으로 생성했습니다.
그래서 미탐이 실제로 납니다. 예외 가정은 "구조화 공격자는 화면에 뜨는 건당 한도를 안다" 하나뿐입니다.

| 안 | 정탐율 | 보류율 | 탐지 오탐율 |
|---|---:|---:|---:|
| A 규칙만 | 82.7% | 13.1% | 0.0% |
| B z-score만 | **22.2%** | 1.4% | 0.8% |
| C 규칙+z (멘토링 시점) | 87.0% | 13.9% | 0.8% |
| **D C+구조화+매칭 (현재 앱)** | **91.4%** | 13.9% | 0.8% |
| E D+Isolation Forest (오프라인 전용) | 93.8% | 14.3% | 1.2% |

### 발표에서 쓸 수치 5개

1. **C → D: 정탐율 87.0 → 91.4%, 오탐은 1건도 늘지 않았다** (253건 동일)
2. **z 단독은 사칭 5%, 청구서 조작 24%밖에 못 잡는다** — "z를 버린다"가 아니라 **"z는 금액 축 하나로만 쓰고 나머지 축을 따로 만든다"**
3. **한도를 바짝 묶은 가구에서 z의 구조화 정탐율은 정확히 0%** → 구조화 탐지가 메우는 사각지대 (D는 78%)
4. **차단 시점** 2.4번째 → 2.0번째, **유출액 29% 감소**
5. **z=3의 근거** = 오탐율 1.37% 지점

### 부수 발견

보류의 최대 원인인 '월 누적 한도 초과' 160건 중 **120건이 사기가 한도를 먼저 소진해
뒤따르는 정상 결제가 막힌 연쇄**입니다. 사기의 2차 피해가 *"어머니가 정작 필요한 병원비를
못 쓰는 것"* 으로 나타납니다.

### 먼저 말할 한계

1. **합성 데이터 자체 평가**이며 실거래 성능이 아닙니다. 이상치 비율 8.2%도 설정값입니다.
2. **E안(Isolation Forest)은 오프라인 평가 전용이고 앱에 탑재하지 않았습니다.**
3. 공격 유형은 상정한 4종뿐입니다.
